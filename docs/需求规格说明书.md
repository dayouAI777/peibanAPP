## ① 项目概述

一款「先捏人、再养感情」的 AI 虚拟陪伴 App：用户填一份详细设定，生成一个专属陪伴角色（参考图自己上传），之后像微信一样聊天，角色记得住你们聊过的事，还会偶尔主动找你说话。

解决的是：通用 AI 助手没性格、聊完就忘、你不找它它就不理你。第一卖点锁定 **「专属感 + 主动惦记你」**。

## ② 用户画像

| 项 | 内容 |
|---|---|
| 目标用户 | 【AI建议】用户本人及小范围内同样需要情绪出口的朋友；成年人 |
| 使用场景 | 【AI建议】晚上回家、通勤、睡前，打开聊几句；或收到 TA 主动发来的一句惦记 |
| 痛点 | 【AI建议】工具味太重、记不住你、真人社交有成本；想要一个稳定、不评判、记得住自己的对象 |
| 定位边界 | 自用 / 小范围分享，不商用、不上架、不做付费、不做账号体系 |

## ③ 版本迭代规划

**V1 MVP（已实现）**
- 三步角色设定表单（TA 是谁 / 你们俩 / 边界）
- 用 DeepSeek 把表单整理成「人设 + 第一句开场白」；断网或未填 Key 时用本地模板兜底
- 从相册上传人物参考图（复制进 App 私有目录）
- 一对一文字聊天，带人设与最近 20 条上下文
- 角色主动发消息：预约本地通知 → 点开后现场生成
- 本机保存角色、聊天记录、Key、设置
- 设置页：Key、主动消息开关 / 每天条数 / 时段、随机度、清空记录、删除角色

**V2**：长期记忆（自动提炼「重要的事」）、多角色切换、聊天记录搜索、主动消息内容风格可选、语音播报。
**V3**：语音输入、云端同步、角色分享、iOS 正式打包、可选的文生图接口。

**裁剪说明**：语音、多角色、长期记忆、云账号会显著拉长周期并引入后台复杂度，主动裁到 V2/V3，保证 V1 先能打包跑起来。用户明确要的「详细设定生成人物」「主动发消息」两项 V1 全留。

## ④ 页面文字原型

| 页面 | 标题 / 主要组件 | 文字内容 | 按钮与跳转 |
|---|---|---|---|
| **欢迎页** | 「有人在这儿等你」；图标、副文案、右上角设置齿轮 | 「写细一点，TA 就更像你心里那个人。会记得你们聊过的事，也会偶尔主动找你。」 | 「创建我的陪伴者」→ 设定页；已有角色时多一个「继续和 XX 聊天」→ 聊天页，并提示「重新创建会清空现在的聊天记录」；齿轮 → 设置页 |
| **设定页**（3 步） | 进度条 `1/3 · 说说 TA 是谁`；第 1 步：名字*、称谓、年龄感、身份、外貌气质、性格标签多选、说话风格、上传参考图；第 2 步：TA 怎么称呼你、关系选项、初见场景、主动程度滑杆；第 3 步：避讳话题、补充设定、说明卡片 | 「不接生图服务，图只存在这台手机上」「没填 API Key 也能先建好角色」 | 「上一步」回退；「下一步」→ 下一分步（第 1 步名字必填）；「生成 TA」→ 调 DeepSeek 出草稿 → 结果页 |
| **结果页** | 参考图大图、名字、开场白卡片、可展开的人设全文 | 本地兜底时提示「去设置填 Key，回来点换一句」 | 「换一句」→ 重新调 DeepSeek；「改设定」→ 回设定页（保留已填内容）；「就开始聊天吧」→ 落库 + 发第一句 + 排通知 → 聊天页 |
| **聊天页**（主页） | 顶部头像 + 名字 + 「正在输入…/在这儿」；消息气泡（用户右 / 角色左，主动消息带「主动找你」小标签）；输入框 + 发送；报错横条 | 输入提示「说点什么，或者只是打个招呼」 | 「发送」→ 带上人设和最近上下文调 DeepSeek → 追加气泡；齿轮 → 设置页；从通知点进来 → 自动生成一条主动消息 |
| **设置页** | API Key 输入框（可显隐）、主动消息开关 / 每天条数 / 时段、随机度滑杆、保存、清空记录、删除角色 | 「Key 只存在这台手机上，不会上传到任何地方」「把 APK 发给朋友时，对方填自己的 Key 就行」 | 「保存设置」→ 写本机 + 重排通知 + 提示「存好了」；「清空聊天记录」/「删除这个 TA」→ 二次确认弹窗 → 执行；删除后回欢迎页 |
| **通知落地** | 无独立页面，复用聊天页 | 通知引子如「在吗，刚想到你」「忽然有点惦记你」 | 点通知 → 打开 App → 定位聊天页 → 现场生成一条主动消息 |

**页面流转**：欢迎页 → 设定页 → 结果页 → 聊天页 ↔ 设置页；系统通知 → 聊天页（带主动消息）。

## ⑧ 技术选型方案

> 已在本机实测通过：Flutter 3.50.0 / Dart 3.14.0 · JDK 21 · Android SDK 36 · Gradle 9.5.0 · AGP 9.3.1 · flutter_local_notifications 22.3.3。
> 通知插件选 22.x 而非最新的 23.x，是因为 23.x 要求 compileSdk 37，而 Android 37 平台包当时尚未发布。

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | Flutter（Dart）【AI建议】 | 一套代码双端；聊天列表性能好；V1 只打 Android，但代码不含任何 Android 专属调用，iOS 随时能补 |
| 对话模型 | DeepSeek `deepseek-chat` | 用户指定；OpenAI 兼容格式，换模型只改两行常量 |
| 人设生成 | 同一个 DeepSeek 接口 | 一次调用返回 `{persona, greeting}` JSON；失败或没填 Key 时用本地模板兜底，创建流程不卡顿 |
| 人物参考图 | `image_picker` + 复制到私有目录 | 用户指定「自己上传」；避开相册临时路径失效 |
| 本地数据库 | `sqflite` | 角色卡 + 聊天记录，聊天场景够用 |
| 设置存储 | `shared_preferences` | Key、频率、时段、随机度 |
| 状态管理 | `provider` + `ChangeNotifier` | V1 够用，依赖少 |
| 主动消息 | `flutter_local_notifications` + `timezone` 预约 | 不需要服务器、不需要后台常驻；点开才联网生成，两端都稳 |
| 时区 | 固定 `Asia/Shanghai`【AI建议】 | 自用默认国内；人在国外改 `proactive_service.dart` 一行 |

**主动消息的取舍（重要）**：iOS 不允许 App 常驻后台静默联网，Android 也常被省电策略掐掉，所以不做「后台定时拉大模型」。改成「预约本地通知 → 用户点开 → 那一刻生成」。代价是通知本身只是一句引子、不是模型生成的完整消息；换来的是两端都能跑、不用服务器、不用保活。这个取舍在 V1 是值得的。

**API Key 安全**：Key 由用户在设置页填写、只写进本机，不硬编码、不进仓库、不进 APK。自用与「小范围分享」场景下这是最省事的方案；代价是每个人填自己的 Key。若要对外分发且不想让用户各自申请 Key，才需要加后端代理，那属于 V3。
